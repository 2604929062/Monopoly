# 玩家交易设计

## 目标

为《新城地产局》加入玩家间地产与现金交易，支持谈判和交换，同时保持服务端权威结算，不允许交易产生负现金或重复转让资产。

## 方案

采用单一待处理报价的轻量方案。复杂版游戏中，任意存活玩家可以向另一名存活玩家提出交易；目标玩家可接受或拒绝，发起者可撤回。每局同一时间只允许存在一笔待处理报价，避免资产同时出现在多份报价中。暂不实现自由聊天、还价链、竞价或自动超时。

报价双方可各自提供：

- 现金，金额为非负整数；双方合计不能为零。
- 一项或多项地产；地产必须属于提供方，且未抵押、没有建筑。
- 可将现金与地产组合。

任何有效报价至少包含一方提供正现金或地产。禁止向自己报价、向破产玩家报价、交易破产玩家资产，以及在大厅或游戏结束后交易。

## 报价生命周期

1. 发起者提交目标玩家、双方现金金额和双方地产编号。
2. 服务端校验房间、玩家、现金格式、地产所有权及可交易状态；报价不冻结资产或现金。
3. 目标玩家接受或拒绝；发起者可在处理前撤回。
4. 接受时服务端重新校验双方当前现金与地产状态。任一资产已不可用时，交易不执行，报价清除并向双方说明原因。
5. 校验通过后，在一次状态变更中扣款、转移地产、更新日志并广播完整房间状态。

## 状态与接口

- 将待处理交易作为房间级状态，而非公开写入 `GameState`；通过独立 Socket 事件广播，避免公开任何不必要的玩家私有信息。
- 创建、接受、拒绝、撤回事件均由共享 Zod schema 校验，并校验 socket 身份与 `playerId` 一致。
- 服务端处理任何行动前校验交易参与者身份；仅目标玩家可接受或拒绝，仅发起者可撤回。
- 房间状态更新时广播待处理报价；新加入或重连玩家也应收到当前报价。
- 交易完成或终止后广播交易结果，并写入现有城市动态/游戏日志。

## 前端交互

- 游戏界面提供“交易”入口，展示可交易的对手和地产。
- 报价编辑器分为“我提供”和“我想要”，现金使用整数输入，地产使用多选项。
- 收到报价时突出展示双方给付内容，并提供接受、拒绝操作；发起者看到撤回操作。
- 待处理报价期间仍可正常进行其他游戏操作；若导致报价失效，在接受时清晰提示并清除报价。
- 破产玩家不可发起或接收交易；未轮到玩家也可以交易。

## 验证

- 规则测试覆盖合法组合、现金不足、非所有者地产、抵押/有建筑地产、破产玩家和非法金额。
- 服务端测试覆盖房间隔离、身份校验、参与人权限、报价失效、重连广播与一次性结算。
- 浏览器端验证发起、收到、接受、拒绝和撤回流程，并至少使用多客户端验证对手视图一致。
- 完成后运行 `pnpm test`、`pnpm typecheck`、`pnpm build` 和 `git diff --check`。

## 首版不包含

简化版交易、贷款债务转移、抵押地产转让、带建筑地产转让、议会规则投票、赌场交易、聊天或还价。
